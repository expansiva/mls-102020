- 2026-07-31 — **T4 template-readiness lint + T6 coverage telemetry (improveNewSolution, session B)**. New pure module `templateLint.ts` (11 tests) runs at e7, where every workspace and operation already exists and the SET can be judged: per classified workspace it asks whether the contract satisfies the `minimumRequired` its page category declares, so the l2 renderer can use the category template instead of the generic fallback. **The inegotiable rule is enforced by construction**: the lint only ever rewrites a bffCall OUTPUT ENVELOPE — it never adds/removes/edits an entity, a rule or an operation (a test diffs everything outside `presentation`/`output` before and after, and the dry run over the 14 real 102045 workspaces reports `business untouched: true`). Outcomes: `ok` | `repaired` (a `list` output lifted into a paginated envelope, item columns unchanged; no invented `total`, because `<op>.total` may not exist in the operation and would produce a `from` the e6 gate cannot resolve) | `downgraded` (business semantics missing => fall back to the best ALTERNATE that the contract actually satisfies, recorded in classificationNote) | `unready` (`templateReady: false`, generic fallback) | `skipped` (category has no minimumRequired yet, or no catalog — warn, never judge). A downgrade never lands on a category without a `minimumRequired`: claiming readiness nobody can verify is worse than admitting not-ready. **Universal rule (category-independent)**: a REQUIRED id input on a command with no source, or `source: userDecision`, is a finding — the 102045 billingWorkspace defect (`projectId required` with no picker became a typed-in text box). It is reported, NOT auto-repaired: the fix is a picker query reusing another workspace's browse operation (which would break the e6 equality/coverage gates if injected here) or a navigation contract — both are site-map decisions, not contract form. **Ordering matters**: the lint runs BEFORE the closing artifacts because `emitNsBffContracts` derives the wire contracts from these same workspaces (repairing after the emit would ship stale contracts); repaired workspaces are rewritten whole, so `sliceHash` and every untouched field survive. **T6**: `buildNsTemplateCoverage` + `renderNsTemplateCoverage` persist `l4/{module}/trace/template-readiness.json` per run and append the workspace x category x confidence x templateReady table to `e7-validation.md`; aggregated across projects it answers the catalog-evolution questions (an orphan page with confidence < 6 in 2+ projects = candidate for a NEW category; a category that keeps being downgraded = candidate for a split). Schema bump v3/v7 for `presentation.templateReady` (written by this lint, never by the model). Data (session B prerequisite): `minimumRequired` written for the 5 categories with REAL evidence only — inventoryControl/productCatalog/approvalWorkflow (the three active 102040 template cells, quoting their §Minimum required) + operationsQueue/dashboardCommandCenter (analise1 scores 9/10); each block carries `evidence` and a `note` saying what was deliberately LEFT OUT because it needs judgment (a "readable label", "a price charged to the buyer"). The other 27 categories have no block and are skipped with a warning, by design. **Dry run over the real 02:46 102045 run (14 workspaces)**: 1 ok, 13 skipped, 3 id-without-source findings (invoiceWorkspace projectId+clientId, projectLifecycleWorkspace clientId), zero crashes, business untouched. That 13/14 skip rate is itself the T6 signal: the classifier gravitates to entityRecordManagement (3x), readOnlyDetailPortal (3x) and financialTransactions (2x) — the categories that most deserve the next templates.
